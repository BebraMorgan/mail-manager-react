# /problems — проблемные письма

Источник: последний backend `mail-manager-single-admin` (без API пользователей/ролей).

## API

- `GET /api/queue/problems?limit=200` — максимум 200 последних писем, которые имеют `retry`, `skipped`, `needs_review`, `importance=uncertain`, `deletion_state=moving/unknown`. Без серверной пагинации. Фильтры и поиск локальные; значения на карточках относятся **только к загруженным записям** и могут пересекаться.
- `GET /api/mail/delete-audit` — последние 50 событий в журнале.
- `GET /api/classifications/:id` — детальная классификация; возможен `404` для неготовых писем.
- `POST /api/classifications/:id/retry` — только при **ручном подтверждении**; действие ставит письмо в очередь, не классифицирует синхронно.
- `POST /api/mail/delete/:id/reconcile` с `{ "resolution": "in_inbox" | "moved_to_trash", "password": "..." }` — только после внешней проверки письма в Яндекс Почте, для состояния `deletion_state=unknown`. Данный POST **не перемещает письмо в IMAP**, а лишь фиксирует проверенную человеком информацию в SQLite.

## Архитектура

- `features/problems/api` — вызовы Go API.
- `features/problems/store` — Zustand с фильтрами, результатами, журналом, error/loading и сбросом при смене сессии.
- `features/problems/hooks` — автообновление, повторная классификация, сверка, получение детали.
- `features/problems/components` — UI: таблица, индикаторы, диалог сверки, журнал.
- `pages/Problems` — сборка страницы.

Содержимое письма не хранится в Zustand. Для письма с готовой классификацией переиспользуется `MailDrawer` (BODY.PEEK в IMAP); для остальных показывается причина ошибки и доступность повторного задания. Автообновление раз в 45 секунд, при возвращении вкладки и по кнопке.

## Проверка

```sh
npm run lint
npm run build
```

Для `reconcile` сначала вручную сверить местоположение письма на стороне Яндекса. Никогда не выбирать решение по предположению из логов, не делать авто-повтор IMAP MOVE.
